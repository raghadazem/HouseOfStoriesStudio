## 1. What Was Completed

- **Database layer** (`app/core/db/`): declarative `Base`, `UUIDPrimaryKeyMixin` + `TimestampMixin`, 8 enums, and a SQLite engine/session factory that enables `PRAGMA foreign_keys=ON` on every connection via a per-engine event listener (never global, so it can't leak into unrelated engines a test might create).
- **All 11 required domain models** (`app/core/models/`), each with a UUID primary key and `created_at`/`updated_at`: `Character`, `CharacterVersion`, `CharacterReference`, `Episode`, `Scene`, `Short`, `Asset`, `PromptTemplate`, `ProductionTask`, `ApprovalRecord`, `LicenseRecord` — plus two many-to-many association tables (`episode_characters`, `scene_characters`). Full field-by-field rationale in `docs/09_DOMAIN_MODEL.md`; full column/constraint reference in `docs/10_DATABASE_SCHEMA.md`.
- **`Asset` validation**: `relative_path` is validated (not absolute under POSIX *or* Windows conventions, no `..` traversal, backslashes normalized) and `checksum` is validated (64-char lowercase sha256 hex) via SQLAlchemy `@validates`, so bad data is rejected immediately in Python rather than only on flush.
- **Alembic migrations** (`alembic/`): `env.py` resolves the database URL from `app.config.get_config()` at runtime (respecting `HOS_DATA_DIR`) rather than a hardcoded path in `alembic.ini`, and enables the same foreign-key pragma. `render_as_batch=True` is set, which SQLite requires for most schema changes. One migration exists (`37154bea36d1_initial_schema.py`, autogenerated and verified against the models with `alembic check`). Upgrade → downgrade → upgrade round-trip verified manually and by an automated test.
- **Seed data** (`app/core/db/seed.py`): Melissa, Bilsan, Episode 001, and its 3 Shorts. Melissa/Bilsan's identity fields (name, age, role, traits, basic appearance) come verbatim from `docs/02_CHARACTER_BIBLE.md`; their `CharacterVersion` rows are explicit **placeholders** (`status=draft`, `master_prompt=None`, `color_palette=[]`, a `"PLACEHOLDER"`-flagged `visual_summary`) since no approved artwork exists yet — nothing here should be mistaken for a finalized design. Episode 001's titles/lesson/runtime come from the founder's Milestone 2 approval message. Idempotent: re-running `seed_demo_data()` reuses existing rows rather than duplicating them. Runnable standalone via `python -m app.core.db.seed` (which refuses to run with a clear `RuntimeError` if migrations haven't been applied yet).
- **Privacy**: no personal reference photographs exist anywhere in this milestone's code, tests, fixtures, or seed data — see `docs/11_STORAGE_RULES.md` §4 for the storage-level rule this milestone's schema was built to support (enforcement in the GUI/import flow is Milestone 3+).
- **49 new automated tests** (74 total including Milestone 1's 25), covering exactly the categories requested: relationships (cascades, many-to-many, back-populates), migrations (upgrade/downgrade/drift-check via a real `alembic` subprocess), seed data (content correctness + idempotency), Arabic UTF-8 round-tripping (names, dialogue), uniqueness (every unique constraint in the schema has a test attempting to violate it), validation (`Asset` path/checksum rules), duplicate assets (checksum and relative_path collisions both rejected), and relative paths (absolute-path/traversal rejection, Windows-style paths, separator normalization).
- Updated Milestone 1's `tests/unit/test_repo_structure.py` guardrail to also cover the new `app/core/db/`, `app/core/models/`, and `alembic/` structure.
- `ruff check .` clean (generated Alembic revision scripts under `alembic/versions/` are excluded from linting — see `pyproject.toml` — since they follow Alembic's own template style, not this project's).

## 4. Database Schema

Full reference: `docs/10_DATABASE_SCHEMA.md`. Summary: 13 tables (11 entity tables + 2 many-to-many association tables), all UUID-keyed, all foreign-key-enforced, zero binary columns. See `docs/09_DOMAIN_MODEL.md` for the entity-relationship diagram and per-model rationale.

## 5. Assumptions Made

1. **`Scene.location` is a free-text string, not a foreign key to a `Location` table.** The approved Milestone 2 model list didn't include `Location`, and `docs/03_WORLD_BIBLE.md`'s locations aren't modeled yet — keeping it a plain string avoids inventing a model that wasn't asked for. Flagged as an open question below.
2. **`ApprovalRecord.entity_id` has no foreign key**, by design (see `docs/09_DOMAIN_MODEL.md`) — it's polymorphic across entity types, which SQLite/SQLAlchemy can't express as a single FK constraint. This is a deliberate simplicity trade-off (one small table vs. one approval table per approvable entity), not an oversight.
3. **`Asset.created_at` doubles as "imported date"** rather than adding a separate `imported_at` column, since they're the same moment for every asset in this system (there's no "staged but not yet imported" state).
4. **Episode 001's `includes_song` defaults to `false`** — the founder's seed-data instructions didn't specify whether Episode 001 has an original song, so it was left at the schema default rather than guessed.
5. **No `Scene` or `PromptTemplate` rows were seeded for Episode 001** beyond what was explicitly requested (Melissa, Bilsan, Episode 001, 3 Shorts) — adding invented scene content would have violated "do not generate creative content."

## 6. Open Questions

- Should `Scene.location` become a proper `Location` model (mirroring `docs/03_WORLD_BIBLE.md`'s Melissa's House / Forest / Butterfly Lake / Rainbow Bridge / Tree House / Moon Garden) in a later milestone, with its own reference-art folder like characters have? Left as free text for now since it wasn't in the approved Milestone 2 model list.
- `PromptTemplate.character_id`/`episode_id`/`scene_id` are all independently nullable — should a prompt be required to relate to *something*, or is a fully-generic reusable prompt (e.g. a pure style-lock block tied to nothing) a valid real-world case? Current schema allows it; no constraint enforces a choice.
- `LicenseRecord` currently allows multiple records per asset (no uniqueness) — intentional (license status can be re-verified over time) but worth confirming that's the desired history-keeping behavior rather than a single mutable record per asset.
